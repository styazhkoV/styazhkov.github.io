## 🎯 Постановка задачи

Основная цель проекта заключалась в обеспечении бесперебойного обмена данными между устаревшим легаси-модулем на **Oracle** и новым микросервисом. Заказчик столкнулся с проблемой: существующая система не могла эффективно взаимодействовать с современными сервисами через REST API.

### Ключевые требования

- Обеспечить real-time синхронизацию данных
- Минимизировать нагрузку на legacy-систему
- Реализовать отказоустойчивый механизм повторных попыток
- Предусмотреть логирование всех операций

## 🛠 Проектирование решения

### Схема данных (Entity Relationship)

Для реализации задачи была разработана следующая структура таблиц:

| Поле          | Тип данных    | Описание                    |
| :------------ | :------------ | :-------------------------- |
| `USER_ID`     | NUMBER (PK)   | Уникальный идентификатор    |
| `TRANS_DATE`  | TIMESTAMP     | Дата и время транзакции     |
| `STATUS`      | VARCHAR2(20)  | Текущий статус обработки    |
| `RETRY_COUNT` | NUMBER        | Количество попыток отправки |
| `LAST_ERROR`  | VARCHAR2(500) | Последняя ошибка            |

### Архитектура интеграции

Была выбрана паттерн **Change Data Capture (CDC)** с использованием Oracle Streams для отслеживания изменений в исходной таблице. Это позволило:

1. Избежать polling-запросов к базе данных
2. Гарантировать порядок обработки транзакций
3. Минимизировать задержки в доставке данных

## 🔄 Описание API методов

Был спроектирован набор методов для взаимодействия с микросервисом:

### GET /api/v1/transaction/{id}

Получение статуса транзакции по идентификатору.

**Response (200 OK):**

```json
{
  "id": "12345",
  "status": "COMPLETED",
  "updated_at": "2026-01-25T15:00:00Z"
}
```

### POST /api/v1/transaction

Создание новой транзакции.

**Request:**

```json
{
  "user_id": 12345,
  "amount": 1500.0,
  "currency": "RUB",
  "description": "Payment for services"
}
```

**Response (201 Created):**

```json
{
  "id": "67890",
  "status": "PENDING",
  "created_at": "2026-01-25T14:30:00Z"
}
```

## 📊 Результаты

После внедрения решения были достигнуты следующие показатели:

- **99.9%** uptime интеграционного слоя
- **< 500ms** среднее время обработки транзакции
- **0** потерянных транзакций за 6 месяцев эксплуатации

## 🔑 Ключевые выводы

1. CDC-подход значительно снижает нагрузку на legacy-системы
2. Детальное логирование критически важно для отладки интеграций
3. Механизм retry с exponential backoff предотвращает каскадные сбои
